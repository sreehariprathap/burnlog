# Social — Friends & Leaderboard — Design

## Problem

Burnlog already has a full solo gamification loop — XP, levels, streaks (`lib/leveling.ts`, `ConsistencyTracker`) — but no social layer at all. There is no way to connect with other users or compare progress. Streaks and levels are stickier when compared against people you know; this spec adds a friends system and a leaderboard on top of the existing gamification data, without exposing any workout/food/finance detail.

## Goals

- Users can find each other by username, send/accept/decline friend requests, and unfriend.
- Users can see a leaderboard of their accepted friends (+ themselves), ranked by three switchable metrics: XP, current streak, and this week's active-day count.
- Every user gets an auto-generated, later-editable username so the feature works immediately without an onboarding step.

## Non-goals

- Activity feed / milestone posts ("Alex hit a 7-day streak") — leaderboard shows numbers only, no feed or storage for events.
- Blocking or reporting — unfriending (deleting the `Friendship` row) is the only moderation action in v1.
- Groups/teams — friendship is 1:1 only, no shared-group leaderboards.
- Any Lifelog (finance) data — this feature is scoped entirely to Burnlog fitness data.
- Cross-user visibility into raw logs (workouts, meals, weight) — only `xp`, `level`, `currentStreak`, and weekly-active-day count are ever exposed to friends.

## Data model

```prisma
model Profile {
  // ...existing fields
  username String @unique
}

/// friend relationship — one row per requested pair; deleted on unfriend/decline
model Friendship {
  id          String    @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  requesterId String    @db.Uuid
  addresseeId String    @db.Uuid
  status      String    @default("pending") // 'pending' | 'accepted'
  createdAt   DateTime  @default(now())
  respondedAt DateTime?

  requester Profile @relation("FriendshipRequester", fields: [requesterId], references: [id])
  addressee Profile @relation("FriendshipAddressee", fields: [addresseeId], references: [id])

  @@unique([requesterId, addresseeId])
  @@map("friendships")
}
```

- No `LeaderboardEntry` table — the leaderboard reads `Profile.xp` / `Profile.currentStreak` directly, and computes weekly-active-days on demand (see below). There is nothing to keep in sync.
- Declining a request or unfriending both simply `DELETE` the `Friendship` row — no soft-delete/status history in v1.
- `@@unique([requesterId, addresseeId])` prevents duplicate outgoing requests in the same direction; the API layer also checks the reverse direction before insert (see below) so A→B pending blocks B→A pending.

## Username generation & settings

- Generator: `slugify(firstName) + '_' + 4-char random base36 suffix` (e.g. `sree_x7k2`). On collision (unique constraint violation), retry with a new suffix, up to 5 attempts, then fail loudly (should be statistically unreachable).
- **Backfill migration**: existing `Profile` rows get a username generated by the same function as part of the migration that adds the column (required since the column is `@unique` non-null).
- **New signups**: username generated at profile-creation time.
- **Editing**: a new "Username" field on the existing `/profile` settings page, with a debounced availability check (`GET /api/social/username-available?u=...`) before save. Editing does not affect existing `Friendship` rows (keyed by `profileId`, not username).

## API routes

All under `app/api/social/`, all using the existing `createRouteHandlerClient` + `supabase.auth.getUser()` auth pattern already used by the AI routes. `requesterId`/`addresseeId` and any "current user" identity is always resolved server-side from the authenticated session — never trusted from the request body.

- `GET /api/social/username-available?u=` — availability check for the settings page.
- `GET /api/social/search?q=` — prefix search on `username`, excludes self, existing friends, and pending requests either direction. Returns `{ id, username, firstName, level }[]`.
- `POST /api/social/requests` — body `{ addresseeUsername }`. Rejects: self-request, addressee not found, a `Friendship` already existing in either direction (pending or accepted) — each with a specific error the UI maps to a disabled-button state rather than a raw error string.
- `GET /api/social/requests` — incoming pending requests for the current user.
- `POST /api/social/requests/:id/accept` — sets `status = 'accepted'`, `respondedAt = now()`. Only the addressee may accept.
- `POST /api/social/requests/:id/decline` — deletes the row. Only the addressee may decline.
- `DELETE /api/social/friends/:friendshipId` — unfriend; either party may call this on an `accepted` row.
- `GET /api/social/friends` — accepted friends: `{ id, username, firstName, avatarUrl, xp, level, currentStreak }[]`.
- `GET /api/social/leaderboard?metric=xp|streak|weekly` — friends + self, sorted server-side by the requested metric, each row annotated with rank.

## Leaderboard computation

- **`xp` / `streak` metrics**: direct read/sort of `Profile.xp` / `Profile.currentStreak` for the caller + accepted friends. No new computation.
- **`weekly` metric**: reuses the existing week-activity logic from `ConsistencyTracker` (`computeConsistencyWeek`, `getWeekRange`, querying `TABLES_WITH_DATE` — `sessions`, `calorie_burns`, `food_intakes`, `step_entries`, `stamina_sessions`, `weight_entries`) — same query shape, but parameterized over all of the caller's friends' `profileId`s (plus their own) in one batch instead of just the caller's own.
- Own rank is always included/highlighted in the response even if it falls outside a future top-N cutoff (no cutoff in v1 — friend lists are expected to be small).

## UI

- New route `app/(burnlog)/social/page.tsx`:
  - Friend search + pending-requests section at top (incoming requests with accept/decline; outgoing shown as "pending").
  - Leaderboard card below, using the existing `@radix-ui/react-tabs` dependency for the XP / Streak / Weekly tab switcher.
  - Empty state ("No friends yet — search for someone to add") shown instead of a blank leaderboard when the friends list is empty.
- New 5th tab in `components/BottomNav.tsx`: `{ href: '/social', label: 'Social', Icon: UsersIcon }`. The floating pill nav will need slightly tighter icon/label spacing to fit 5 tabs — a CSS sizing tweak, not a structural change.
- New "Username" field added to the existing `/profile` settings page.

## Error handling & edge cases

- Duplicate/self/already-friends requests rejected with specific 400 messages; UI disables the relevant action instead of surfacing a raw error where the state is already known client-side (e.g. searching your own username).
- Username availability race (two users claim the same name in the same instant): DB unique constraint is the source of truth; the settings-page save catches the constraint violation and re-prompts, the debounced pre-check is only a UX nicety.
- A friend deletes their account: `Friendship` rows cascade-delete is **not** assumed — `onDelete` behavior for the two `Profile` relations should be `Cascade` so orphaned rows can't linger (matches the existing `ProgramWeek → Program` cascade pattern in the schema).
- Accept/decline/unfriend on a `Friendship` row the caller isn't part of returns 403/404, not a silent no-op.

## Testing

No automated test suite exists in this repo. Manual verification:
- Two test accounts: search by username, send a request, confirm it appears as pending on the sender and incoming on the recipient.
- Accept a request, confirm both accounts now see each other under `/api/social/friends` and on the leaderboard.
- Decline a request, confirm the `Friendship` row is gone and a new request can be sent again afterward.
- Unfriend, confirm both accounts' leaderboards update immediately (friend disappears).
- Change XP/streak/log activity on one test account, confirm all three leaderboard tabs (XP, Streak, Weekly) re-rank correctly.
- Edit username in `/profile` settings, confirm friend search/requests still resolve correctly under the new name.
- Attempt to accept/decline a request that isn't addressed to the current user (e.g. via direct API call) and confirm it's rejected.
