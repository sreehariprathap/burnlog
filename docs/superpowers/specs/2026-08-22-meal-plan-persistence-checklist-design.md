# Persisted Meal Plan + Per-Day Checklist — Design

**Date:** 2026-08-22
**Status:** Approved design, pending spec self-review

## Goal

Today, `MealPlanWidget` (on BurnLog's Goals page) generates a 7-day AI meal plan on demand, but never persists it — reload the page and it's gone, and it's entirely absent from `/session` (Plan)'s per-day view. Users have no durable way to see "what am I eating today/this week." This adds persistence and a per-day interactive checklist to the Plan tab.

## Non-Goals

- Grocery list / weekly budget / nutrition summary persistence — these stay ephemeral (shown right after generating, not stored). Deliberate scope cut, not a regression.
- Any interaction between meal check-ins and `FoodIntake`/calorie goal math. The "eaten" checkbox is a separate, purely informational tracker.
- Changes to the AI prompt/model logic in `app/api/ai/meal-plan/route.ts` beyond adding a persistence step after generation.
- LifeLog grocery-list generation (a distinct, already-deferred LifeLog sub-project) — unrelated to this BurnLog nutrition feature.

## Decisions (locked during brainstorming)

1. **Interactivity:** Per-meal checkboxes, scoped to the actual calendar date (not the weekday), separate from FoodIntake logging.
2. **Generation surface:** Relocated entirely from Goals into `/session` (Plan) — removed from Goals' `goalTabs`, not duplicated.

## Data model

```prisma
/// weekly meal plan — one row per profile+weekday+mealType, regenerated by upsert (mirrors WorkoutPlan's dayOfWeek pattern)
model MealPlanEntry {
  id          String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  profile     Profile  @relation(fields: [profileId], references: [id])
  profileId   String   @db.Uuid
  dayOfWeek   Int      // 0=Sun..6=Sat
  mealType    String   // 'breakfast' | 'lunch' | 'dinner' | 'snack'
  name        String
  description String?
  calories    Int?
  protein     Float?
  carbs       Float?
  fat         Float?
  prepMinutes Int?
  createdAt   DateTime @default(now())

  @@unique([profileId, dayOfWeek, mealType])
  @@map("meal_plan_entries")
}

/// per-date "did I eat this" checkbox state — deliberately separate from FoodIntake/calorie logging
model MealPlanCheckIn {
  id        String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  profile   Profile  @relation(fields: [profileId], references: [id])
  profileId String   @db.Uuid
  date      DateTime @db.Date
  mealType  String
  eaten     Boolean  @default(true)
  createdAt DateTime @default(now())

  @@unique([profileId, date, mealType])
  @@map("meal_plan_checkins")
}
```

`Profile` gains `MealPlanEntry[]` and `MealPlanCheckIn[]` relations. RLS added to both tables via the same per-profile loop already used for every other table in `supabase/rls.sql`, applied via `mcp__supabase__apply_migration` (this session has live Supabase access, same as the LifeLog finance tables).

`MealPlanEntry` is keyed by **weekday**, matching `WorkoutPlan`'s existing convention (a repeating weekly template). `MealPlanCheckIn` is keyed by **actual date**, matching `WaterEntry`'s `@@unique([profileId, date])` convention — checking off this Monday's breakfast must not pre-check next Monday's.

## Generation flow (`app/api/ai/meal-plan/route.ts`)

Unchanged: builds the prompt from `Profile.lifestyle.nutrition`/`.grocery`, calls the AI model, returns `{ weekPlan, groceryList, estimatedWeeklyBudget, nutritionSummary }`.

New step before returning: for each `DayPlan` in `weekPlan` (day name → 0-6 via a `DAY_NAME_TO_INDEX` map) and each present meal (`breakfast`/`lunch`/`dinner`/`snack?`), upsert into `meal_plan_entries` with `onConflict: 'profileId,dayOfWeek,mealType'` — mirrors `AddWorkoutModal`'s existing upsert against `workout_plans`. A day/meal slot not present in the new response is left alone (no explicit delete step) — regenerating fills in what the AI returns; scope doesn't require handling partial-week regeneration UX beyond that.

## UI changes

**Goals page** (`app/(burnlog)/goals/page.tsx`): remove the `'meal-plan'` entry from `goalTabs` and delete its slide; `MealPlanWidget` is removed from `_components` (moved, not duplicated — see below).

**Session/Plan page** (`app/(burnlog)/session/page.tsx`): new `MealChecklist` component (new file, adapted from `MealPlanWidget`'s generate-button/loading UI) rendered for the **selected day**, in both branches:
- Today branch (alongside `PlanCard`/`WorkoutChecklist`): after the existing workout checklist.
- Other-day branch (`PlanDaySummary`): after the summary card.

`MealChecklist` behavior for the selected `(profileId, dayOfWeek, selectedDate)`:
- Fetches `meal_plan_entries` for that `profileId`+`dayOfWeek`.
- If none exist: shows the "Generate My Meal Plan" CTA (same copy/loading state as today's `MealPlanWidget` empty state) — generating calls `/api/ai/meal-plan`, which persists all 7 days at once; the component then refetches just the selected day's rows.
- If entries exist: renders each meal (breakfast/lunch/dinner/snack, in that fixed order, skipping absent ones) as a row — name, description, calories/macros, prepMinutes — with a checkbox bound to `meal_plan_checkins` for `(profileId, selectedDate, mealType)`. Toggling upserts/deletes that check-in row (checked → upsert `eaten:true`; unchecked → delete the row, so absence = not eaten, keeping the table sparse like `WaterEntry` isn't but similar to how `FoodIntake` rows only exist when logged).
- A "Regenerate" affordance re-runs generation for the whole week (same upsert path), available whenever entries already exist for the profile (not just the selected day) — checking any single day doesn't block regenerating the rest.

## Error handling

- AI generation failure: same existing error surface as `MealPlanWidget` today (inline error message, retry via the same button) — the persistence step only runs after a successful AI response, so a failed generation never partially writes bad data.
- Check-in toggle failure (network/RLS): revert the checkbox's optimistic UI state and show a small inline error, consistent with how other toggles in this codebase (e.g. `Switch` components) are handled — no existing global toast pattern for this class of error, so inline is the established convention.
- No entries for a given weekday but the profile has entries for other weekdays (partial week / stale data after a schema change): treated identically to "no entries" — shows the generate CTA for that day specifically.

## Testing

- No test framework in this repo (established convention) — verification is `npx next build` + manual walkthrough: generate a plan from Session/Plan, confirm entries appear for every weekday when paging through `WeekdayTabs`, confirm checking a meal persists across a reload, confirm unchecking removes it, confirm Goals page no longer shows the "Meal Plan" tab.
- `mcp__supabase__list_tables` confirms `meal_plan_entries`/`meal_plan_checkins` exist with `rls_enabled: true`, same as prior schema work.

## Rollout order

1. Prisma schema (2 models) + RLS.
2. Persist step added to `app/api/ai/meal-plan/route.ts`.
3. `MealChecklist` component (fetch entries + check-ins, render, toggle).
4. Wire `MealChecklist` into `/session` (both today and other-day branches).
5. Remove the Meal Plan tab from Goals; delete the old `MealPlanWidget` (superseded by `MealChecklist`, which absorbs its generate-button UI).
